# 0. 怎么用这份文档

这份文档把整个项目从「是什么」讲到「每一行大概在干什么」，目标是：**你完全没基础也能看懂，看完能用专业术语讲出来答辩**。

阅读建议：先看第 1~3 章建立整体印象（架构、为什么这么做），再看第 5、6、7 章（协议、线程、网络）——这三章是答辩最容易被问的硬核；第 9、10 章是"数据怎么流动、每个功能怎么实现"；最后第 15 章是**答辩问答速记**，临场前背一遍。

一句话总览：**这是一个"客户端—服务器"架构的局域网即时通信软件。一个 C 语言写的多线程服务器在中间转发消息、用 MySQL 存数据；每个用户用一个 Electron 桌面程序连上服务器收发消息。**

# 1. 这个项目是什么

- **名字**：zoo（猛兽派对风格的聊天软件），课程设计题目是"基于多线程并发的网络即时通信工具"。
- **能干什么**：注册/登录（账号或邮箱）、加好友（申请—同意）、私聊、群聊、离线消息、历史记录、好友备注/拉黑/删除、建群/邀请入群/群公告/群成员、个人资料（昵称/生日）、换头像、消息检索、上下线通知、消息免打扰、置顶、从列表移除等。
- **形态**：一台机器跑**服务器**（Linux），多台机器跑**桌面客户端**（Windows/Linux 都行），客户端填服务器 IP 即可互相聊天。

**为什么做成"客户端—服务器（C/S）"而不是两台电脑直接连？**
因为要支持"很多人同时在线、A 给离线的 B 发消息、群里一条消息发给所有成员、历史记录要存下来"。这些都需要一个**中心节点**来统一管理在线状态、转发、存储。这个中心节点就是服务器。

# 2. 系统总体架构

整个系统分三层：

```
┌──────────────────────────┐        ┌──────────────────────────┐
│  桌面客户端 A (Electron)  │        │  桌面客户端 B (Electron)  │
│  渲染进程: 界面(HTML/JS)  │        │  ...                      │
│  主进程  : Node + TCP     │        │                           │
└───────────┬──────────────┘        └───────────┬──────────────┘
            │  TCP (定长 Message 4240 字节)       │
            └───────────────┬────────────────────┘
                            ▼
            ┌────────────────────────────────────┐
            │      C 多线程服务器 (chat_server)    │
            │  主线程: accept 接新连接             │
            │  每个客户端 -> 一个工作线程(pthread) │
            │  在线表(内存) / 转发 / 业务逻辑      │
            └───────────────┬────────────────────┘
                            │  SQL
                            ▼
            ┌────────────────────────────────────┐
            │            MySQL / MariaDB           │
            │  users / friends / chat_groups /     │
            │  messages / offline_msg / ...        │
            └────────────────────────────────────┘
```

**三层各自的职责**（这是答辩要点）：

1. **客户端（表示层）**：只负责"画界面 + 把用户操作变成一条协议消息发出去 + 把收到的消息显示出来"。它**不直接碰数据库**，所有数据都向服务器要。
2. **服务器（业务逻辑层 + 转发层）**：处理登录鉴权、好友/群关系、把消息转发给在线的人、给不在线的人存离线消息、所有历史落库。**它是唯一和数据库说话的人。**
3. **数据库（持久层）**：把用户、好友、群、消息等"需要长期保存"的东西存在硬盘上，服务器重启数据也不丢。

**为什么这样分层？**
- **安全**：客户端拿不到数据库密码，不能直接改库，所有操作都要经过服务器校验（比如"你是不是这个群的成员""对方是不是把你拉黑了"）。
- **一致性**：只有服务器一个人写库，避免多客户端同时乱写造成冲突。
- **可扩展**：要加功能只改服务器和客户端的协议，数据库结构相对稳定。

# 3. 技术选型与理由

| 部分 | 用了什么 | 为什么这么选 |
|---|---|---|
| 服务器语言 | **C** | 课程要求；贴近系统调用（socket/pthread），能体现"多线程并发"考核点 |
| 并发模型 | **pthread 多线程**（每连接一线程） | 实现简单直观，能讲清楚临界区/互斥锁；连接数不大时足够 |
| 网络 | **TCP + Socket** | 聊天要求消息**可靠、不丢、不乱序**，TCP 正好保证；UDP 不保证可靠 |
| 数据库 | **MySQL/MariaDB** | 关系型，天然适合"用户-好友-群-消息"这类有关系的数据；课程常用 |
| 密码 | **SHA‑1 摘要** | 不存明文密码；课程示例够用（生产应用 bcrypt/argon2） |
| 客户端外壳 | **Electron** | 用网页技术(HTML/CSS/JS)写漂亮界面，又能打包成桌面 .exe/AppImage；VS Code、Discord 都是这套 |
| 客户端界面 | **HTML/CSS/JS** | 开发快、样式自由，能做出"猛兽派对"风格 |
| 客户端↔服务器 | **Electron 主进程 Node 的 TCP** | 浏览器不能开裸 TCP，但 Electron 主进程是 Node，可以直接连服务器的 TCP，无需中间桥接 |

**为什么客户端不用浏览器直接连？**
浏览器只能用 HTTP/WebSocket，开不了裸 TCP，而服务器用的是裸 TCP + 自定义二进制协议。Electron 的"主进程"本质是 Node.js，能开 TCP，所以让主进程连服务器、界面（渲染进程）通过"进程间通信(IPC)"找主进程收发。这样就**不需要额外的转发服务、也不占用 localhost 端口**。

# 5. 通信协议设计（重点）

## 5.1 为什么要"自定义协议"

A 和 B 要通过服务器对话，就必须约定"一条消息长什么样、怎么知道这是登录还是聊天"。这套约定就是**协议**。本项目用了一个**固定大小的结构体**当作"统一信封"。

## 5.2 Message 结构（一条消息的格式）

所有交互（无论登录、聊天、加好友）都用**同一个结构体**，靠 `type` 字段区分含义。定义在 `common/protocol.h`：

| 字段 | 类型/大小 | 含义 |
|---|---|---|
| `type` | uint32 (4B) | 消息类型（见 MsgType），决定这条消息是干什么的 |
| `status` | uint32 (4B) | 应答码 / 或复用作"文件大小""申请号"等 |
| `group_id` | uint32 (4B) | 群号（群聊相关时用） |
| `body_len` | uint32 (4B) | body 实际字节数 |
| `from_name` | char[32] | 发送者账号（6 位数字字符串） |
| `to_name` | char[32] | 接收者账号 |
| `from_nick` | char[32] | 发送者昵称（服务器填好，客户端直接显示） |
| `timestamp` | char[32] | "YYYY-MM-DD HH:MM:SS" |
| `body` | char[4096] | 正文（文本 / 多行列表 / 二进制） |

合计 = 16 + 32×4 + 4096 = **4240 字节**（`MSG_SIZE`）。

**为什么用"定长结构体"而不是变长？**
- **简单可靠**：收发时永远"读满 4240 字节就是一条完整消息"，**天然解决 TCP 粘包/拆包**问题（不用自己设计长度前缀+解析）。
- **跨语言一致**：C 服务器按内存布局直接收发；客户端（`msgcodec.js`）按同样的偏移量小端编解码，两边对得上。
- **代价**：哪怕只发"hi"也要传 4240 字节，有点浪费。但教学项目里清晰 > 省流量，这是个合理取舍（答辩可主动说出这个权衡）。

## 5.3 消息类型 MsgType（节选）

| 值 | 名称 | 含义 |
|---|---|---|
| 1/2/3 | REGISTER/LOGIN/LOGOUT | 注册/登录/退出 |
| 4 | RESPONSE | 服务器统一应答（status=结果码，body=描述） |
| 10/11 | PRIVATE_CHAT / GROUP_CHAT | 私聊 / 群聊 |
| 21/22/23/24 | FRIEND_DEL/LIST/BLACK_ADD/DEL | 删好友/好友列表/拉黑/取消拉黑 |
| 25/26/27/28/29 | FRIEND_REQ/NOTIFY/REPLY/LIST/REMARK | 好友申请/通知/答复/待处理列表/备注 |
| 30/32/33/39 | GROUP_CREATE/LIST/MEMBERS/INVITE | 建群/群列表/群成员/邀请入群 |
| 40/41/42 | HISTORY_PRIV/GROUP/OFFLINE_PULL | 历史私聊/历史群聊/离线消息 |
| 60/61 | NOTIFY_ONLINE/OFFLINE | 好友上线/下线通知 |
| 70/71/90 | USER_SEARCH/GROUP_SEARCH/MSG_SEARCH | 用户/群/消息检索 |
| 100/101/102/103 | GROUP_NOTICE/PROFILE_GET/SET/DATA | 群公告/资料查询/设置/资料数据 |

## 5.4 寻址规则与账号生成

- **账号** = `100000 + 数据库里的用户 id`。第一个注册的人是 `100001`。这样账号是 6 位、对外稳定，又不暴露内部自增细节。
- `from_name`=发送者账号，`to_name`=接收者账号，`from_nick`=昵称（服务器填，客户端直接显示，省去再查一次）。

## 5.5 应答码 RespStatus

`RS_OK=0, RS_FAIL=1, RS_AUTH_FAIL=2, RS_USER_EXIST=3, RS_USER_NOT_FOUND=4, RS_NOT_FRIEND=5, RS_IN_BLACKLIST=6, RS_GROUP_NOT_FOUND=7`。客户端看 `status` 就知道成功还是哪种失败。

# 6. 进程与线程模型（重点·考核点）

## 6.1 服务器：主线程 + "每连接一线程"

`server.c` 的主线程做一件事：循环 `accept()` 等新客户端。**每来一个客户端连接，就 `pthread_create` 创建一个新线程**去专门伺候它（`handler.c::client_thread`），然后主线程立刻回去 `accept` 下一个。

```c
while (g_running) {
    int cfd = accept(g_listen_fd, ...);     // 等一个新客户端
    pthread_t tid;
    int *arg = malloc(sizeof(int)); *arg = cfd;
    pthread_create(&tid, NULL, client_thread, arg);  // 开一个线程伺候他
}
```

每个工作线程一开始 `pthread_detach(自己)`，意思是"我结束后自动回收，不用别人 join"。线程里是一个循环：`recv_msg` 收一条 → `switch(type)` 处理 → 继续收，直到对方断开。

**为什么"每连接一线程"？**
- 这样**A 在发消息时不会卡住 B**——每个人有自己的线程，互不阻塞，这就是"并发"。
- 实现直观，最能体现课程的"多线程 + 互斥锁"考核点。
- 缺点：连接特别多（上万）时线程开销大；本课程规模够用（答辩可提"高并发可改用 epoll + 线程池"）。

## 6.2 三处"临界区"与互斥锁（最重要的答辩点）

多个线程同时跑，就会有"大家抢同一份共享资源"的问题。被多个线程同时读写的代码叫**临界区**，必须用**互斥锁(mutex)**保证"同一时刻只有一个线程进去"，否则数据会乱（竞态条件）。本项目有三处：

1. **在线用户表**（`online.c` 的 `g_mu`）：所有线程都要读/改"谁在线、用哪个 fd"，加锁。
2. **数据库连接**（`db.c` 的 `g_dbmu`）：只有一条 MySQL 连接，多个线程不能同时用它发 SQL，所以每次查询都先锁、查完解锁，**把所有 SQL 串行化**。
3. **同一个 socket 的写**（`online.c::online_push` 里的 `write_mu`）：可能同时有人给同一个在线用户发私聊和群聊，两个线程同时往同一个 fd 写会把字节交错弄坏，所以写之前加锁。

> 这正好对应课程里的**临界区 / 互斥 / 生产者-消费者**知识点：工作线程是"生产者"（产生要发给某人的消息），通过加锁安全地写入对方的 socket。

## 6.3 客户端：主进程 + 渲染进程

Electron 程序本身是**两个进程**：
- **渲染进程**（Chromium）：跑 `zoo-chat.html`，就是你看到的界面。出于安全，它不能直接用 Node/网络。
- **主进程**（Node）：开 TCP 连服务器、读写字节。

两者通过 **IPC（进程间通信）** 对话：`preload.js` 用 `contextBridge` 给界面开一个小窗口 `window.zooNative`（只有 connect/send/onMsg/win 四个方法）。界面要发消息 → 调 `zooNative.send(对象)` → 经 IPC 到主进程 → 主进程编码成 4240 字节发给服务器；服务器来的消息 → 主进程解码 → 经 IPC `onMsg` 回调推给界面。

**为什么这么分？** 安全隔离：界面（可能加载第三方内容）拿不到 Node 的全部能力，只能用我们开放的受控接口，防止被恶意脚本利用。

# 7. 网络与可靠收发

## 7.1 TCP 是"字节流"，会粘包

TCP 只保证字节按序到达，但**不保证一次 read 就正好读到一条消息**：可能两条消息粘在一起，也可能一条被拆成两次到。本项目用"**定长 4240 字节**"彻底回避：永远"凑满 4240 字节算一条"。

## 7.2 io_all：循环读/写直到读满/写完

`common/net_io.c` 的核心是一个循环：

```c
while (left > 0) {
    n = do_read ? read(fd, p, left) : write(fd, p, left);
    if (n == 0) return -1;            // 对端关闭
    if (n < 0) { if (errno==EINTR) continue; return -1; } // 被信号打断就重试
    left -= n; p += n;                // 还没读/写完就接着来
}
```

- `send_msg` = 把 4240 字节**全部**写出去；`recv_msg` = 把 4240 字节**全部**读进来。
- 处理了"短读短写"（一次没读/写完）和被信号打断（EINTR）的情况，这是网络编程的基本功，答辩常问。

## 7.3 SIGPIPE 屏蔽

往一个已被对方关闭的 socket 写数据，系统会发 `SIGPIPE` 信号默认杀掉进程。服务器 `signal(SIGPIPE, SIG_IGN)` 忽略它，改为让 `write` 返回错误自己处理，**避免一个客户端掉线把整个服务器搞崩**。

# 8. 数据库设计

`sql/init.sql` 建了下面这些表（关系型数据库的核心是"表 + 表之间的关系"）：

| 表 | 关键字段 | 作用 |
|---|---|---|
| `users` | id, nickname, password(sha1), **email(唯一)**, avatar_color, **birthday**, online | 用户账号。账号=100000+id |
| `friends` | user_id, friend_id, status(0好友/1拉黑), **remark** | 好友关系（**双向各存一行**，便于反查），含备注 |
| `chat_groups` | id, name(唯一), owner_id, **notice** | 群，含群主、群公告 |
| `group_members` | group_id, user_id | 群成员（多对多） |
| `messages` | id, from_id, target_id, msg_type(0私/1群), content, sent_at | **所有聊天记录**。私聊 target=对方 id，群聊 target=群号 |
| `offline_msg` | user_id, message_id | 离线队列：某人不在线时，要发给他的消息 id 先记这里 |
| `friend_requests` | from_id, to_id, hello, status(0待/1同意/2拒) | 好友申请 |
| `group_join_requests` | group_id, user_id, hello, status | 入群申请 |

**几个设计要点（答辩可讲）：**
- 好友关系**双向存两行**（A→B 和 B→A），这样"查我的好友"和"查谁加了我"都很快。
- 聊天记录统一进 `messages` 一张表，用 `msg_type` 区分私聊/群聊，`target_id` 复用为"对方 id 或群号"，结构简洁。
- 离线消息只存 `message_id` 引用，不复制正文，省空间；用户上线后按 id 取出再删。
- `email` 唯一索引保证"一个邮箱只能注册一个账号"。

# 9. 数据流详解（端到端时序）

下面用"一步步发生了什么"讲清楚几个核心流程。

## 9.1 启动与连接

1. 服务器：`bin/chat_server` 启动 → 连 MySQL → 监听 8888。
2. 客户端：Electron 启动 → 主进程读登录页填的"服务器地址" → `net.connect(IP, 8888)` → 连上后通知界面"已连服务器 ✅"。

## 9.2 注册（账号或邮箱唯一）

```
界面: 填昵称/邮箱/密码 -> zooNative.send({type:1, body:"昵称\n密码\n邮箱"})
主进程: 编码4240字节 -> TCP -> 服务器
服务器(handler MSG_REGISTER): 拆出昵称/密码/邮箱
   -> 若邮箱已存在: 回 RESPONSE(status=3 邮箱已注册)
   -> 否则 db_register(): 密码 SHA1 入库, 自动加"小助手/新手指南"为好友
   -> 回 RESPONSE(status=0, body=新账号如"100007")
界面: 收到账号 -> 自动用账号+密码登录
```

## 9.3 登录 + 登录后初始化推送

```
界面: zooNative.send({type:2, body:"账号或邮箱\n密码"})
服务器(MSG_LOGIN): 含'@'按邮箱查, 否则按账号查; 密码SHA1比对
   成功 -> 记入在线表(online_add) -> 回 RESPONSE(body="账号\n昵称")
   紧接着主动推送(让客户端一进来就有数据):
     - 好友列表(22)    - 群列表(32)
     - 待处理好友申请(28) - 待处理入群申请(37)
     - 离线消息(逐条 10/11)  - 给我的好友广播"我上线了"(60)
界面: 一一接收并渲染会话列表/联系人/红点
```

## 9.4 发私聊（在线 vs 离线）

```
界面: zooNative.send({type:10, to_name:"100008", body:"你好"})
服务器(do_private):
   1) 查对方 id; 若对方把我拉黑 -> 回 RESPONSE(status=6) 拒发
   2) db_save_msg() 先把消息存进 messages 表(无论在不在线都要存历史)
   3) 对方在线? online_push 直接转发给对方的 socket
      对方离线? db_offline_put 进离线队列, 等他上线再推
   4) 回 RESPONSE(status=0 "sent") 给发送方
对方界面: onMsg 收到 type=10 -> 找到/新建与我的会话 -> 显示气泡
```

## 9.5 群聊

```
界面: zooNative.send({type:11, group_id:5, body:"集合"})
服务器(do_group): 查群成员 -> 存库 -> 逐个成员: 在线就推、离线就入离线队列(自己不发给自己)
```

## 9.6 历史记录

打开会话时，客户端发 `HISTORY_PRIV`(对方账号) 或 `HISTORY_GROUP`(群号)；服务器从 `messages` 查出来按时间逐条回推（每条是一个 PRIVATE_CHAT/GROUP_CHAT，带 `to_name` 以便客户端归类到正确会话）。

## 9.7 好友申请（P2P 体现）

```
A 申请: send({type:25, to_name:B}) -> 服务器存 friend_requests, 给B推 FRIEND_REQ_NOTIFY(26)
B 界面: "新的朋友"区显示验证信息 + 同意/拒绝
B 同意: send({type:27, status=申请号, group_id=1})
服务器: 双向加好友 -> 分别给 A、B 推新的好友列表(22)
之后 A、B 即可互发消息(真正的端到端聊天)
```

## 9.8 上下线通知

某人登录/断开时，服务器找出"把他加为好友的人"，给在线的那些人推 `NOTIFY_ONLINE(60)`/`NOTIFY_OFFLINE(61)`，对方界面把好友状态点变绿/变灰。断开是在工作线程结束时（`out:` 标签）统一处理。

# 10. 各功能实现详解（前端 → 协议 → 服务端 → 数据库 → 为什么）

> 统一模式：界面把操作变成一条 `Message` 发给服务器；服务器校验+改库+（必要时）推送；客户端收到推送刷新界面。

- **注册/邮箱唯一/邮箱登录**：见 9.2/9.3。`users.email` 唯一索引保证唯一；登录时按是否含 `@` 选择"邮箱查"或"账号查"。*为什么*：邮箱比 6 位账号好记，唯一性防重复注册。
- **私聊/群聊**：见 9.4/9.5。*为什么先存库再转发*：保证不在线也能拿到历史与离线消息。
- **离线消息**：`offline_msg` 队列，上线时 `db_offline_take` 取出推送并删除。*为什么*：人不在也不丢消息。
- **历史记录**：`messages` 表 + `HISTORY_*`。客户端"删除会话"只是本地隐藏(`hidden` 标记)，重新打开仍能从服务器拉回历史——*因为*真实消息在库里，没删。
- **好友申请/同意/拒绝**：`friend_requests` + 25/26/27/28；同意时**双向**写 `friends`。
- **好友备注**：`friends.remark` + `MSG_FRIEND_REMARK(29)`；好友列表多一列带回备注，客户端在会话列表/聊天标题显示备注优先。
- **拉黑/删除好友**：`friends.status=1`/删行 + 23/21；被拉黑者再发私聊返回 `RS_IN_BLACKLIST(6)`。
- **建群/邀请/群成员/群公告**：`chat_groups`/`group_members` + 30/39/33/100。邀请前校验"我是不是群成员"；群公告只有群主能改（校验 `owner_id`）。
- **个人资料(昵称/生日)/查看他人资料**：`users.birthday` + 101/102/103。
- **换头像/换群头像**：界面里选本地图片→画到 canvas 裁成正方形→转 dataURL 存本地；按账号持久化，登录后恢复。*为什么本地*：头像是展示，先保证体验；可扩展为上传服务器（协议已留 `AVATAR_*`）。
- **消息检索**：`MSG_SEARCH(90)` 服务端在我参与的所有消息里 `LIKE` 关键字；客户端"查找/文件"面板还能按 图片/文件/日期 在本会话筛选。
- **上下线通知/未读红点/免打扰/置顶/从列表移除**：见上；免打扰会话不计未读；置顶排到列表顶部；从列表移除只隐藏不删消息。

# 11. 安全性

- **密码不存明文**：`db.c::sha1_hex` 把密码做 SHA‑1 摘要再入库，登录时比对摘要。
- **防 SQL 注入**：所有用户输入拼进 SQL 前都过 `mysql_real_escape_string`（`db.c::esc`），把引号等特殊字符转义，防止恶意输入篡改 SQL。
- **客户端权限隔离**：Electron `contextIsolation` + preload 受控接口，界面拿不到 Node 全权限。
- **业务校验在服务端**：拉黑、群成员、群主权限等都在服务器判断，客户端改不了。

# 12. 关键并发点小结（答辩高频背诵）

| 共享资源 | 在哪 | 锁 | 不加会怎样 |
|---|---|---|---|
| 在线用户表 | `online.c` | `g_mu` | 增删时表错乱、读到野 fd |
| MySQL 连接 | `db.c` | `g_dbmu` | 单连接被多线程同时用，结果错乱/崩溃 |
| 同一 socket 写 | `online_push` | `write_mu` | 两条消息字节交错，对端解析失败 |

模型：主线程 `accept` + 每连接 `pthread` 工作线程 + `pthread_detach` 自动回收；用互斥锁保护临界区。

# 15. 答辩问答速记（高频）

**Q：整体架构？** 客户端—服务器（C/S）三层：Electron 桌面客户端（界面+主进程TCP）、C 多线程服务器（转发+业务）、MySQL（持久化）。客户端不直连数据库，全部经服务器。

**Q：并发怎么做的？** 主线程 `accept`，每个客户端连接 `pthread_create` 一个工作线程并 `detach`；三处共享资源（在线表、DB 连接、socket 写）用互斥锁保护临界区。

**Q：为什么用 TCP？怎么处理粘包？** 聊天要可靠有序，TCP 保证；用**定长 4240 字节 Message**，"读满一条"天然避免粘包，配合 `io_all` 循环处理短读短写。

**Q：消息怎么从 A 到 B？** A 发到服务器→服务器存库→B 在线就推、离线进 `offline_msg`，B 上线再取。群聊对每个成员重复此逻辑。

**Q：离线消息？** 接收方不在线，消息 id 入 `offline_msg`；登录时取出推送并删除，所以不丢。

**Q：账号怎么来的？** `100000 + users.id`，第一个人 100001。

**Q：密码安全？防注入？** 密码 SHA‑1 摘要入库不存明文；SQL 前 `mysql_real_escape_string` 转义防注入。

**Q：客户端为什么是 Electron 不是浏览器？** 浏览器开不了裸 TCP，Electron 主进程是 Node 能直连服务器；同一套 HTML 界面打包成桌面应用。

**Q：邮箱唯一/邮箱登录怎么实现？** `users.email` 唯一索引；注册先查重；登录按是否含 `@` 决定按邮箱或账号查询。

**Q：服务器崩溃风险点？怎么防的？** 客户端掉线写 socket 会触发 SIGPIPE → `SIG_IGN` 忽略；DB/在线表加锁防竞态；`recv_msg` 返回 -1 即线程退出并清理。

**Q：还能怎么优化？** 高并发用 epoll+线程池替代每连接一线程；密码换 bcrypt；头像/文件走专门的二进制上传；协议可加版本号。

# 16. 小白词典

- **C/S 架构**：客户端(Client)—服务器(Server)，客户端连服务器要数据。
- **进程/线程**：进程是一个运行中的程序；线程是进程里能并行干活的"分身"。
- **并发**：多件事看起来同时进行（多线程实现）。
- **临界区/互斥锁**：多个线程都要碰的共享数据叫临界区；锁保证同一时刻只有一个线程进去。
- **Socket / TCP**：网络通信的"插口"；TCP 是可靠、有序的传输协议。
- **粘包**：TCP 字节流里多条消息粘一起/被拆开，需要自己分界（本项目用定长解决）。
- **IPC**：进程间通信，这里指 Electron 界面进程和主进程对话。
- **持久化**：把数据存到硬盘（数据库），重启不丢。
- **SHA‑1**：把任意内容变成固定长度"指纹"的算法，用来存密码摘要。
